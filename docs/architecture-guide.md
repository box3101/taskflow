# TaskFlow 아키텍처 입문 — 후임이랑 같이 보는 큰 흐름

> 목표: "체크박스 하나 누르면 무슨 일이 벌어지나"를 화면부터 DB까지 끝까지 따라가며 이해하기
> 대상: 이제 막 웹 개발 시작한 사람. 용어는 나올 때마다 쉬운 말로 풀어요.

---

## 0. 시작 전에 — 딱 3가지 용어만

이거 3개만 알면 나머지는 다 따라와요.

| 용어 | 진짜 뜻 | 쉬운 비유 |
|------|---------|-----------|
| **프론트엔드(Front-end)** | 사용자 눈에 보이는 화면. 브라우저에서 돌아감 | 매장 직원 (손님 응대) |
| **백엔드(Back-end)** | 화면 뒤에서 판단·저장하는 프로그램. 서버에서 돌아감 | 본사 (실제 처리·보관) |
| **HTTP / JSON** | 프론트↔백엔드가 대화하는 방법 / 대화 내용의 포맷 | 전화 통화 / 대화 내용 |

**제일 중요한 감각 하나:**

> 프론트엔드와 백엔드는 **완전히 다른 프로그램**이에요. 서로 남남이고, 오직 **HTTP 요청(JSON)** 으로만 대화합니다.
> 매장 직원(프론트)과 본사(백엔드)가 **전화(HTTP)** 로만 소통하는 것과 똑같아요.

```
[프론트엔드]  ←── 전화(HTTP) ──→  [백엔드]  ←──→  [DB]
  화면 보여줌                     판단·처리        저장
```

---

## 1. 전체 지도 (한 장 요약)

체크박스를 클릭하면 이 순서로 흘러가요. **이 그림 하나가 이 문서의 전부**예요.

```
[브라우저] Vue 화면
    │  ① 사용자가 체크박스 클릭
    ▼
[api/client.ts] axios           ← 여기서 로그인 토큰 자동으로 붙임
    │  ② HTTP 요청 (PATCH /todos/5)
    ▼
━━━━━━━ 인터넷 ━━━━━━━
    │
[app.ts] Express 서버           ← 요청 받는 대문. 어느 담당한테 보낼지 정리
    │  ③ "/todos 요청이네 → todos 담당한테"
    ▼
[middleware/auth.ts]            ← 문지기: "너 로그인 했어?"
    │  ④ 통과하면 "이 사람 3번 유저" 정보를 심어줌
    ▼
[routes/todos.ts]               ← 실무자: "본인 것 맞나? 값이 이상하진 않나?" 검증 후 처리
    │  ⑤ prisma.todo.update(...)
    ▼
[Prisma] SQL 번역기             ← JS 코드를 DB 언어(SQL)로 통역
    │  ⑥ UPDATE todos SET done=true...
    ▼
[PostgreSQL] 데이터베이스        ← 진짜 저장되는 곳 (Railway 클라우드)
    │
    └─── 결과(JSON)가 위 순서를 거꾸로 타고 화면까지 돌아옴 → 체크 표시 갱신 ───
```

## 2. 프론트엔드 — "화면 + 요청 심부름꾼"

프론트는 딱 **3층**으로 되어 있어요.

| 층 | 파일 | 역할 | 비유 |
|----|------|------|------|
| **입구** | `router.ts` | 어떤 주소에 어떤 화면 보여줄지 | 건물 안내판 |
| **화면** | `views/TodosView.vue` | 눈에 보이는 것 + 클릭 반응 | 매장 직원 |
| **심부름꾼** | `api/client.ts` | 서버에 요청 보내기 | 배달원 |

### 2-1. 입구: 주소 → 화면 (`router.ts`)

브라우저 주소창에 `/todos`를 치면, "이 주소는 이 화면"이라고 미리 정해둔 표에서 찾아 그려줘요.

```js
{ path: 'todos', component: () => import('./views/TodosView.vue') }
// "/todos 주소로 오면 → TodosView 화면을 보여줘"
```

> 💡 **용어: 라우터(Router)** = "주소 ↔ 화면" 짝을 정해둔 표. 페이지를 새로 불러오지 않고 화면만 바꿔치기해서 빠릿함. (이런 방식을 **SPA**, Single Page Application 이라고 해요.)

이 파일엔 문지기도 하나 있어요 — 로그인 안 했으면 화면 보여주기 전에 로그인 페이지로 튕김:
```js
if (to.meta.requiresAuth && !token) return '/login'
```

### 2-2. 화면: 보여주고 + 반응하기 (`TodosView.vue`)

화면이 뜨는 순간 "내 할일 목록 줘" 하고 서버에 요청해요:
```js
await api.get('/todos')   // GET = "데이터 좀 줘" (읽기)
```

체크박스를 클릭하면 "이거 완료로 바꿔줘" 요청:
```js
await api.patch(`/todos/${todo.id}`, { done: !todo.done })
// PATCH = "일부만 고쳐줘", 뒤의 { done: ... } 가 보내는 값
```

> 💡 **용어: HTTP 메서드** — 요청의 종류. 편지 봉투에 적는 "용건" 같은 거예요.
> | 메서드 | 뜻 | 예 |
> |--------|-----|-----|
> | `GET` | 읽기 (줘) | 할일 목록 조회 |
> | `POST` | 새로 만들기 | 할일 추가 |
> | `PATCH` | 일부 고치기 | 완료 체크 |
> | `DELETE` | 지우기 | 할일 삭제 |

### 2-3. 심부름꾼: 모든 요청의 통로 (`api/client.ts`) ⭐

**여기가 프론트 설계의 핵심**이에요. 모든 요청이 이 한 파일을 거쳐 나가요. 그래서 "매번 반복되는 일"을 여기 한 곳에 몰아넣었어요.

```js
// 요청마다 로그인 토큰을 자동으로 붙여줌
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
```

이 통로가 해주는 3가지:
1. **토큰 자동 첨부** — 매 요청에 "나 로그인한 아무개야" 증표(토큰)를 자동으로 붙임 → 화면 코드는 신경 안 써도 됨
2. **401(=너 누구야) 뜨면 자동 로그아웃** — 토큰 만료되면 알아서 로그인 페이지로 보냄
3. **자동 재시도** — 읽기(GET) 요청이 실패하면 한 번 더 시도

> 💡 **왜 한 곳에 몰았나?** 요청이 화면마다 수십 개인데, 토큰 붙이는 코드를 매번 쓰면 실수하기 쉬워요.
> "공통으로 할 일은 통로 한 곳에 몰고, 화면은 화면만 신경 쓰게" — 이게 좋은 설계의 기본 감각이에요.

## 3. 백엔드 — "문지기 + 판단 + 창고지기"

요청이 서버에 도착하면 **위에서 아래로 차례차례 통과**해요. 백엔드도 3층입니다.

| 층 | 파일 | 역할 | 비유 |
|----|------|------|------|
| **대문/교통정리** | `app.ts` | 요청 받아서 담당한테 분배 | 건물 로비 |
| **문지기** | `middleware/auth.ts` | "로그인 했어?" 검증 | 경비원 |
| **실무자** | `routes/todos.ts` | 진짜 일 처리 (검증·저장) | 담당 부서 |
| **창고 접근** | `prisma.ts` | DB랑 대화 | 창고 관리자 |

### 3-1. 대문: 요청 분배 (`app.ts`)

주소 앞부분을 보고 담당 부서로 넘겨요.

```js
app.use('/todos', todoRouter)      // /todos 로 시작 → todos.ts가 처리
app.use('/projects', projectRouter) // /projects 로 시작 → projects.ts가 처리
```

> 마치 회사 대표번호로 전화하면 "할일 문의는 1번, 프로젝트 문의는 2번" 하고 연결해주는 것과 같아요.

### 3-2. 문지기: 신원 확인 (`middleware/auth.ts`) ⭐

todos.ts 맨 위에 이 한 줄이 있어요:
```js
router.use(authenticate)   // 모든 todos 요청은 이 검문소를 먼저 통과!
```

검문소가 하는 일 — 프론트가 보낸 토큰이 진짜인지 확인:
```js
const decoded = jwt.verify(token, JWT_SECRET)  // 토큰 진위 검증
req.user = decoded   // 통과 → "이 사람 3번 유저"라는 정보를 요청에 심어둠
next()               // 통과! 다음(실무자)으로 보냄
```
토큰이 없거나 가짜면 **여기서 401 반환하고 끝**. 실무자한테 못 감.

> 💡 **용어: JWT (토큰)** = 로그인 성공 시 서버가 발급하는 "출입증". 위조 못 하게 서명이 들어있어요.
> 프론트는 이걸 브라우저에 보관(`localStorage`)했다가 요청마다 내밀고, 백엔드는 매번 진짜인지 검사해요.
> **왜 매번 검사?** HTTP는 "기억력이 없어요". 각 요청은 서로 남남이라, 매번 "나 아까 그 사람이야"를 증명해야 해요.
>
> 💡 **용어: 미들웨어(Middleware)** = 실무자한테 가기 전에 거쳐가는 "중간 처리 단계". 문지기가 대표적. 로그인 검사처럼 **여러 요청이 공통으로 거쳐야 하는 일**을 여기 모아둬요. (프론트의 `client.ts`랑 발상이 똑같죠!)

### 3-3. 실무자: 진짜 로직 (`routes/todos.ts`) ⭐

체크박스 완료 처리(`PATCH /todos/5`)가 여기까지 오면:

```js
// ① 본인 할일 맞는지 먼저 확인 (남의 할일 못 건드리게)
const existing = await prisma.todo.findFirst({ where: { id, userId } })
if (!existing) return res.status(404)   // 없거나 남의 것 → 404

// ② DB 업데이트
const todo = await prisma.todo.update({ where: { id }, data: { done: true } })

// ③ 결과를 JSON으로 돌려줌
res.json({ data: todo })
```

> ⭐ **백엔드에서 제일 중요한 원칙: "프론트가 보낸 값은 절대 그대로 믿지 않는다."**
> 할일 추가 코드(`todos.ts`)를 보면 제목 길이(500자 이내?), 날짜가 진짜 날짜인지, "시작일이 마감일보다 앞인지"까지 전부 **다시** 검사해요.
> **왜?** 프론트 검증은 사용자 편의용일 뿐, 나쁜 사람은 프론트를 건너뛰고 서버에 직접 요청을 날릴 수 있어요. **진짜 방어선은 무조건 백엔드**예요.

### 3-4. 창고 접근: Prisma (`prisma.ts`)

`prisma.todo.update(...)` 이 자바스크립트 한 줄이, 실제로는 이런 DB 언어(SQL)로 번역돼서 데이터베이스로 날아가요:
```sql
UPDATE todos SET done = true, updated_at = now() WHERE id = 5;
```

> 💡 **용어: ORM / Prisma** = SQL을 직접 안 쓰고 **JS 코드로 DB를 다루게 해주는 통역사**.
> SQL 몰라도 `prisma.todo.findMany()` 같은 익숙한 함수로 DB를 쓸 수 있어요.

## 4. DB 계층 — 표의 설계도 (`schema.prisma`)

데이터가 어떤 "표(테이블)" 모양으로 저장되는지 정의한 파일이에요. 엑셀 시트의 열(컬럼) 정하는 것과 같아요.

```prisma
model Todo {
  id      Int      @id           // 각 할일의 고유 번호 (자동 증가)
  userId  Int      @map("user_id") // 누구 할일인지
  title   String                 // 제목
  done    Boolean  @default(false) // 완료 여부 (기본 미완료)
  dueDate DateTime?              // 마감일 (? = 없어도 됨)
  ...
}
```

이 파일 하나가 **① DB 테이블 설계도**이자 **② 코드에서 쓰는 타입의 원천**이에요.
그래서 이걸 바꾸면 → DB에 반영(`db push`) → 코드 타입 갱신(`generate`) 두 단계가 필요해요.

**DB 종류:** 이 프로젝트는 **PostgreSQL**(포스트그레스)을 쓰고, **Railway**라는 클라우드에 올라가 있어요. (내 컴퓨터가 아니라 인터넷 어딘가의 DB 서버)

## 5. 전체를 다시, 한 문장으로

> **화면(Vue)** 이 클릭을 잡아 → **배달원(axios)** 이 토큰 붙여 요청 보내고 → **대문(Express)** 이 담당한테 넘기고 → **문지기(auth)** 가 신원 확인 → **실무자(route)** 가 값 검증하고 → **통역사(Prisma)** 가 SQL로 바꿔 → **창고(PostgreSQL)** 에 저장. 결과는 JSON 되어 왔던 길을 거꾸로 타고 화면까지.

## 6. 같이 보면서 확인하기 (후임 체크 질문)

이거 대답할 수 있으면 큰 흐름은 잡은 거예요:

1. 프론트엔드랑 백엔드는 무슨 방법으로 대화하나요? *(→ HTTP 요청/JSON)*
2. `api/client.ts`(프론트)랑 `middleware/auth.ts`(백엔드)의 공통점은? *(→ 여러 요청이 공통으로 거치는 통로/단계. 반복 로직을 한 곳에 모음)*
3. 프론트에서 이미 "제목 500자 이내"를 검사했는데, 백엔드에서 또 검사하는 이유는? *(→ 프론트는 건너뛸 수 있으니 진짜 방어선은 백엔드)*
4. 로그인 토큰(JWT)은 왜 요청마다 매번 보내나요? *(→ HTTP는 기억력이 없어서 매번 신원 증명 필요)*
5. `prisma.todo.update()`는 실제로 뭐가 되어 DB로 가나요? *(→ SQL 문)*

## 7. 실제 파일 위치 (직접 열어보기)

큰 흐름을 코드로 따라가려면 이 순서로 열어보세요:

| 순서 | 파일 | 뭘 보나 |
|------|------|---------|
| 1 | `frontend/src/router.ts` | 주소 ↔ 화면 짝 |
| 2 | `frontend/src/views/TodosView.vue` | 화면에서 `api.get/patch` 호출하는 부분 |
| 3 | `frontend/src/api/client.ts` | 모든 요청이 거치는 통로 (토큰 첨부) |
| 4 | `backend/src/app.ts` | 요청 분배 (`app.use('/todos', ...)`) |
| 5 | `backend/src/middleware/auth.ts` | 문지기 (토큰 검증) |
| 6 | `backend/src/routes/todos.ts` | 실무 로직 (검증 + prisma 호출) |
| 7 | `backend/prisma/schema.prisma` | 데이터 표 설계도 |

> 팁: 위 순서대로 한 파일씩 열어서 "요청이 지금 어디쯤 와 있나"를 손가락으로 짚으며 따라가면 제일 빨리 이해돼요.
